# Write a repo rule

A repo rule is a mechanism: the `repo-rules` hook checks every shell command or file edit against
it and asks the person (`ask`) or refuses (`deny`). A rule in CLAUDE.md is only text the agent may
forget. Rules live in `rules` of `.ai1/config.json`, which is versioned: the whole team gets them.

## 1. Pin down the rule

From the correction or the CLAUDE.md line, work out, asking only what is missing:

- **what** it catches: a shell command (`on: "bash"`) or an edit to files (`on: "edit"`);
- **how bad** it is: `deny` when it must never happen (generated code, a forbidden tool), `ask`
  when it is sometimes right and the person decides (migrations, deploy scripts);
- **what to do instead**: the message must say why and the right way, because the agent reads it.

## 2. Draft it

```json
{ "id": "use-pnpm", "on": "bash", "pattern": "^npm (install|i|ci)\\b", "action": "deny",
  "message": "this repo uses pnpm: run pnpm install." }
{ "id": "generated-code", "on": "edit", "paths": ["src/generated/**"], "action": "deny",
  "message": "generated by codegen: change the schema and run pnpm codegen." }
{ "id": "no-console-log", "on": "edit", "paths": ["src/**/*.ts"], "pattern": "console\\.log\\(",
  "action": "ask", "message": "use the logger in src/log.ts." }
```

- `id`: kebab-case, unique; it appears in the reason.
- `bash`: `pattern` (JavaScript regex, up to 300 characters) is tested against **each simple
  command** of the line, with quotes removed and words joined by one space, so `cd app && npm i`
  is caught by `^npm i`. Anchor with `^` to avoid matching inside other commands.
- `edit`: `paths` (globs, from the repo root; `*.ts` matches at any depth) limit the files, and the
  optional `pattern` is tested against the new text only (the inserted `new_string` or the written
  content). `paths` alone = any edit to those files.
- Check the pattern against two or three real commands or snippets that must match and two that
  must not, with `node -e` (e.g. `node -e 'console.log(/^npm i\b/.test("npm install"))'`).

## 3. Show it and add it after a yes

Show the person the exact JSON and the examples it catches and lets through. After their yes, add
it to the `rules` list of `.ai1/config.json` with Edit. The `config-guard` hook asks them once more
before the file changes: that prompt is the final approval, never avoid it.

If the rule replaces a line of CLAUDE.md, offer to remove that line (one place for each rule).

## 4. Check it

`ai1 status` must still read the config. A rule that does not validate is ignored with a notice at
the next session start: fix it then. Building the hook input by hand is not needed; the person sees
the rule work the next time it applies.

## Not for

- Destructive commands in general (`rm -rf`, `reset --hard`, force push): the `danger` guard has them.
- Things a linter or a test can check: put them in the verify commands instead.
- Personal preferences: rules apply to everyone who opens the repo.

If Anthropic's `hookify` plugin is installed, it also writes rules (in `.claude/hookify.*.local.md`,
personal); ai1 rules are versioned with the repo. Pick one place per rule.
